# 进销存管理系统（本地部署）

适用于小型超市、小型企业的进销存（采购 / 销售 / 库存）管理软件：**单机部署，多终端通过网络访问**。

一款**纯本地部署**的进销存软件，零外部依赖、零配置，数据全部存在本机 SQLite 文件里。
基于 Web，所以**电脑、手机、平板用浏览器都能用**，对外网访问也只需加一层穿透即可。

> 系统内置的默认商店名称是「天下第一家」，可在「⚙️ 系统配置 → 品牌与开机动画」中改成你自己的店名：页面标题与左侧菜单按「商店名称 + 专用进销存」显示，欢迎语用于打开系统时的开机动画（播完按设定秒数停留并倒计时），还可设置空闲多久后循环播放动画。系统默认以**全屏**方式启动与使用。

## 功能

- 📊 **仪表盘**：今日/本月销售额与利润、库存总值、近 14 天销售趋势、畅销商品 TOP；**库存预警支持勾选后导出 Excel**（表头全选，只导出勾选的商品）
- 📦 **商品管理**：SKU、分类、单位、进/售价、库存、库存下限预警；支持**下载导入模板**、**批量导入**（只导入库里没有的编码），以及**按当前搜索 / 仅看预警导出商品清单**
- ⬇️ **采购入库**：开采购单 → 自动加库存、记成本、写流水
- ⬆️ **销售出库**：开销售单 → 自动减库存、算利润、库存不足拦截；**提交时先查客户预收款：够付就当场抵扣结清，不够才就差额选择收款或挂账**
- 🧾 **单据打印**：开单成功后直接给「打印单据」入口，输出 A4 送货单 / 采购单（含明细、合计、金额大写、定金与已付未付、签字栏），历史单据可在往来单位交易清单里补打
- 📷 **扫码枪录入**：采购/销售单顶部扫码框，扫条码/SKU/名称即自动匹配商品库并加行（重复扫累加数量，支持「编码*数量」）
- 🏷️ **库存管理**：实时库存、低于下限预警、盘点调整（盘盈/盘亏）；支持按**编码 / 名称（模糊）、分类、下限小于、状态（预警/正常）**组合查询，查询结果可导出**盘点表**（刻意不含价格，打印出来手填实盘数）与**库存清单**（含进价、售价、库存金额）
- 🏭 **供应商 / 🧑‍💼 客户**：基础档案维护；**点名称即弹出该单位的交易清单**，可按商品名称模糊查询、按日期段筛选，导出 Excel，并逐单**补打采购单 / 销售单**
- 📈 **报表**：今日/本月销售额与利润、库存总值、近 14 天销售趋势、畅销商品 TOP，支持按日期段统计与 **Excel 导出**
  - 顶部「导出整本报表」导出 9 个工作表（概览 / 应收 / 应付 / 本期采购 / 本期销售 / 库存分类 / 收付款 / 退单 / 改价），无论当前停在哪一页都是同一份完整报表
  - 报表页内三张小表也各有按钮：**库存商品金额（按分类）**支持**打印（A4 纵向、可另存 PDF）**与**导出 Excel**；**本期采购明细 / 本期销售明细**各支持按当前日期段**导出 Excel**，导出内容与屏幕上的同一批单据一致
  - **单家往来流水账**另有独立的「导出路水账」按钮，只导出这一家的明细，日期段与页面完全一致
  - 🔁 **退单报表**：采购/销售退单明细（含「退单待审」锁定单），含退单原因、申请人、审批人与时间，可按状态/关键词筛选
  - 💲 **改价报表**：商品调价、单据改价（让价/加价）、采购进价变动、收付款金额调整记录，给出上调/下调笔数与净影响金额
- 💰 **收付款记账**：采购付款、销售收款，支持**一付多票**（一笔钱分摊到多张单据）、
  **一票多付**（一张单多次付款）、**预付款/预收款**（余款自动挂账、可后续抵扣）、
  **显式定金/首付款**（建单时约定，报表单独列示「定金已付/未付」），并给出应收应付与净头寸统计；
  收付款金额可调整——管理员直接生效，普通用户需管理员审批；
  采购/销售明细均显示**交易时间**与**交易数量**（单品显示「12 台」，多品显示总件数并标注项数，如「13 · 3项」，悬停可看每个商品的数量），默认按时间倒序（最近交易的排在最前）；
  采购应付 / 销售应收两张明细表都支持**按当前查询结果打印**（A4 横向、跨页自动重复表头、可另存为 PDF）与**导出 Excel**，导出的内容与屏幕上看到的是同一批数据；
  **收付款流水**同样支持条件查询（**时间段，默认当天** / 类型 / 往来单位 / 支付方式 / 操作人，日期清空即不限），并按当前条件**打印**与**导出 Excel**，标题处实时给出该条件下的收款合计、付款合计与净额；
  「收付流水账」弹窗里的每一笔也支持**导出 Excel**（含分摊到的单据、本笔转预存、支付方式与操作人）
- 🧾 **退单与审批**：每笔采购/销售可退单，普通用户仅能锁定申请，管理员审批后才回滚库存与资金；采购退单会同时把商品进价还原成「最近一张仍有效的采购单」的价格，并把这次改价从改价报表里撤掉
- 🗑️ **作废与更正**：管理员可对录错的单据直接**作废**（回滚库存、撤销收付款分摊、删除单据本身，快照留痕在 `doc_voids` 表）；也可**删除整笔收付款记录**、修改单据备注；点单号可查看整单明细
- 👥 **用户管理**：管理员可增删用户、分配角色（管理员/普通用户）、重置密码
- ⚙️ **系统配置**：可设置**商店名称**、**开机欢迎语**与**开机动画时长**（欢迎语逐字浮现，播完按设定秒数停留并显示环形倒计时，2~30 秒），可配置**空闲自动播放**（无操作超过设定分钟即循环播放开机动画，任意操作回到原界面，0 = 关闭，最大 99 分钟）；还可勾选是否允许普通用户**退单**、是否允许普通用户**调整收付款金额**（取消勾选后仅管理员可操作）、左侧菜单是否显示当天/当月/当年销售额卡片，以及**登录密码策略**（简单 = 大小写不敏感且无复杂度要求（默认）；中等 = 大小写敏感、无复杂度要求；复杂 = 需 ≥ 8 位且包含大写/小写/数字/符号中至少 3 类）
- 🔐 **登录鉴权**：默认账号 `admin / admin123`，支持改密码
- 💾 **数据备份**：系统配置页「数据安全 · 备份」可一键下载完整数据库快照；服务每天首次启动还会自动备份一份到 `data/backups/`，只保留最近 7 份
- 🩺 **数据体检**：系统配置页「数据体检」一次核对最易出错的账务：分摊是否挂在已退单的单据上、单据有没有被付超、库存有没有负数、单据总额与明细合计是否相符、有没有异常金额的收付款、**有没有哪个单位一边欠着钱一边躺着预存**；每项给出明细清单
- 📋 **库存流水**：库存管理页每个商品可点「流水」，查看采购入库、销售出库、退单回仓、退单退回供应商、作废、盘点调整的完整变动记录（含结存与操作人）；流水累计与当前库存的差额会额外提示（通常是启用前的期初库存）
- 📱 **手机可用**：窄屏下左侧菜单变为底部标签栏，右上角 👤 可改密码、切换全屏、退出登录
- 🖥️ **全屏使用**：进入系统后自动切到全屏，开机动画与日常操作都在全屏下进行；左侧菜单底部的 ⛶ 可随时切换全屏/窗口，Esc 退出全屏（受浏览器限制，全屏需一次点击触发，开机画面会给出提示）

## 快速开始

> **环境要求：Node.js 22 或更高。**
> 依赖 `better-sqlite3@13` 自身声明 `engines.node >= 22`，没有为 Node 18/20 提供预编译二进制。用低版本装依赖时会退化成「从源码编译原生模块」，多数机器因缺少 C++ 构建工具而失败。`package.json` 的 `engines` 已与之一致，避免出现「声明支持 18、实际装不上」的错觉。

```bash
cd inventory
npm install        # 首次安装依赖
npm start          # 启动服务（默认端口 3000）
```

启动后浏览器打开：**http://127.0.0.1:3000**
Windows 用户也可直接双击 `start.bat`（它只会停掉「占用 3000 端口且进程名为 node.exe」的旧进程，端口被别的程序占用时不会误杀）。

> 数据文件位于 `data/inventory.db`，备份时复制该文件即可。删除它会重新生成并写入演示数据。

## 运行测试

```bash
npm test           # 10 个用例，约 1 秒
```

只覆盖两处「算错了也不会抛异常、只会让账慢慢对不上」的地方：

- `test/num.test.js` —— 金额取整口径 `r2`：半值进位方向、正负对称、20 万个三位小数样本逐一比对、NaN/Infinity 不被抹成 0。
- `test/fifo.test.js` —— 批次 FIFO 成本：跨批次计价、剩余均价回写、超量扣减回滚（一点不动）、空库存不覆盖手工进价、报表货值偏差上限。

测试会把 `INVENTORY_DB` 指向系统临时目录并在结束时删除，**不会读写 `data/inventory.db`**。

## 手机 / 局域网访问

1. 电脑和手机连同一个 WiFi。
2. 在电脑上查本机局域网 IP（Windows：`ipconfig` 看「IPv4 地址」，如 `192.168.1.20`）。
3. 手机浏览器访问 `http://192.168.1.20:3000` 即可，界面会自动切换为手机底部标签栏。

## 外网访问（手机随时随地用）

服务本身只跑在本地，要让外网也能访问，任选其一（服务需保持运行）：

### 方案 A：Cloudflare Tunnel（推荐，免费、HTTPS、最稳）
```bash
# 安装 cloudflared 后执行：
cloudflared tunnel --url http://localhost:3000
```
终端会输出一个 `https://xxxx.trycloudflare.com` 域名，发给手机或任何地方打开即可。
（免费临时域名每次重启会变；要固定域名需注册 Cloudflare 账号配置 named tunnel。）

### 方案 B：ngrok
```bash
ngrok config add-authtoken <你的token>   # 官网注册后获取
ngrok http 3000
```
免费版给出随机 `https` 域名，每次启动变化；付费可固定。

### 方案 C：路由器端口映射 + DDNS（适合长期固定）
在路由器做「虚拟服务器 / 端口转发」，把外部端口映射到本机 `3000`；再用 DDNS（如花生壳、No-IP）绑定一个固定域名。
**务必先改掉默认密码**，并对端口做访问控制，避免裸奔。

## 目录结构

```
inventory/
├── server.js            # Express 服务 + 全部 API + 鉴权
├── db.js                # SQLite 表结构与初始数据
├── package.json
├── start.bat            # Windows 一键启动
├── data/                # 数据库文件（自动生成）
│   ├── inventory.db     # 主数据库（WAL 模式）
│   ├── .session_secret  # 会话密钥（首次启动自动生成，删掉等于强制所有人重新登录）
│   └── backups/         # 每天首次启动的自动备份（保留 7 份）
└── public/              # 前端（原生 HTML/CSS/JS，无构建）
    ├── index.html
    ├── css/style.css
    └── js/app.js
```

## 主要接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | 健康检查（**不鉴权**）：返回 `{status, db, uptime, time}`，供 Uptime Kuma 等监控探活；数据库不可读时返回 **503**。刻意不含商品数、单据数等任何业务数据 |
| POST | `/api/login` `/api/logout` | 登录 / 退出 |
| GET | `/api/products` `/api/products?low=1` | 商品列表 / 仅预警 |
| POST/PUT/DELETE | `/api/products[/:id]` | 商品增改删 |
| GET | `/api/products/template` | 下载商品批量导入模板（Excel，数据表仅表头 + 「填写说明」表） |
| GET | `/api/products/export` | 按 `search` / `low=1` 导出商品清单（与页面筛选同一套参数）。「当前库存」刻意不叫「初始库存」，避免导出后导入到另一个库时把库存再叠加一次 |
| POST | `/api/products/import` | 批量导入商品（`{ file: base64, filename }`）。仅导入库中**不存在该商品编码**的行；编码重复（库内已存在 / 本文件内重复）或校验不通过的行进「未导入表」，并随响应返回 `unimported_xlsx`（base64）供下载 |
| POST | `/api/purchases` | 采购入库（事务，自动加库存）。返回里带 `paid` / `outstanding`，提交后能立刻告知「还欠多少」 |
| GET | `/api/purchases/:id` `/api/sales/:id` | 单据详情（含明细行与 `paid` 已付/已收、`outstanding` 未付/未收），单据打印用它 |
| POST | `/api/sales` | 销售出库（事务，扣库存、算利润） |
| GET/POST | `/api/inventory` `/api/inventory/adjust` | 库存查询 / 盘点调整。查询支持 `sku` `name`（模糊）、`category`（精确）、`max_min`（下限严格小于 N）、`status=low\|normal\|all`；兼容旧的 `low=1` |
| GET | `/api/reports/overview` 等 | 报表数据 |
| GET/POST | `/api/inventory/alerts` `/api/inventory/alerts/export` | 库存预警列表 / 导出勾选商品为 Excel（`{ids:[...]}`） |
| GET | `/api/inventory/export` | 库存导出：`mode=stock` 盘点表（无价格，实盘/差异列留空待填）、`mode=full` 完整清单（含成本与售价金额）；筛选参数与 `/api/inventory` 完全相同，导出的就是页面上看到的那批 |
| GET | `/api/reports/returns` | 退单报表（采购/销售，含退单待审；from/to/status/keyword） |
| GET | `/api/reports/price-changes` | 改价报表（单据改价/商品调价/进价变动 + 金额调整；from/to/type/keyword） |
| GET | `/api/reports/export` | 导出 Excel（9 个工作表，含退单明细、改价记录）。这是「整本报表」，各下钻页共用 |
| GET | `/api/reports/stock-value/export` | 导出「库存商品金额（按分类）」为 Excel，复用 `inventoryValue()`，与报表页同一份数据 |
| GET | `/api/reports/period/export` | 导出本期采购/销售明细为 Excel（`?kind=purchase\|sale&from=&to=`），与报表页共用 `periodData()`，导出的就是屏幕上那批单据 |
| GET | `/api/reports/party/:type/:id/ledger` | 单家往来流水账（`from`/`to` 只过滤明细条目；未结清余额始终按全量算，避免筛选后表尾等式自相矛盾） |
| GET | `/api/reports/party/:type/:id/ledger/export` | 导出该单位往来流水账（日期段与页面一致） |
| GET/POST | `/api/payments` | 收付款流水 / 记一笔收付款（含分摊）；GET 支持 `?page=&page_size=` 分页，行为兼容 |
| GET | `/api/party-ledger` `/api/party-ledger/export` | 单家收付款流水（含每笔分摊单据、转预存）/ 导出为 Excel |
| DELETE | `/api/payments/:id` | 删除整笔收付款（仅管理员，连带撤销分摊） |
| POST | `/api/payments/apply-advance` | 用预付款/预收款抵扣某单据 |
| POST | `/api/advance/apply` | 把该单位预存余额按单据先后批量冲抵未结清单据（不新增收付款记录） |
| POST | `/api/purchases/:id/void` `/api/sales/:id/void` | 作废单据（仅管理员：回滚库存、撤销分摊、删除单据，快照写入 `doc_voids`） |
| PUT | `/api/purchases/:id/note` `/api/sales/:id/note` | 修改单据备注（管理员或该单开单人） |
| GET | `/api/finance/summary` | 应收应付、定金统计、预付款余额；明细行含交易数量字段 `qty_total`（总件数）、`item_count`（商品项数）、`qty_detail`（各商品数量明细）、`qty_unit`（单品单位）。收付款流水另接受 `pay_*` 条件（见下两行），并回传 `payments_sum` 小计与 `payments_operators` 操作人候选 |
| GET | `/api/finance/export` | 按与 `summary` **完全相同**的筛选参数导出 Excel，额外用 `kind=purchase\|sale` 选择应付/应收；内部复用同一份汇总计算，保证「页面看到的」与「导出的」是同一批数据。超 2 万行只截断明细，合计仍按全量算并在表头标注 |
| GET | `/api/finance/payments` | 收付款流水（打印取数用）：`pay_from` / `pay_to`（留空=不限）/ `pay_direction`（pay\|receive）/ `pay_party`（`supplier:3` 形式）/ `pay_method` / `pay_operator`；返回筛选后的 `total`、收款/付款/定金小计与明细 |
| GET | `/api/finance/payments/export` | 按同一套 `pay_*` 参数导出收付款流水 Excel（与 `/api/finance/payments`、页面卡片复用同一取数函数） |
| GET | `/api/partners/:type/:id/transactions` | 往来单位交易清单（type=customer/supplier；product/from/to 筛选） |
| GET | `/api/partners/:type/:id/transactions/export` | 导出该单位交易清单为 Excel |
| GET/PUT | `/api/settings` | 系统配置（品牌/动画/权限/销售额/密码策略/侧栏音乐；PUT 仅管理员，支持局部更新） |
| GET | `/api/backup` | 一键备份，下载当前数据库快照（仅管理员） |
| GET | `/api/todo-summary` | 待办汇总（退单待审 / 金额调整待审 / 库存告警） |

### 收付款模型说明
- 一笔收付款（`payments`）对应一个**往来单位**（供应商或客户），金额可**分摊到多张单据**（`payment_allocations`）。
- 一张单据可收付多次（一票多付）；同一笔钱也能分给多张单（一付多票）。
- 收付款未分摊的余额自动成为该单位的**预付款/预收款**；系统会在这笔钱产生时、以及每次新记收付款前，**自动按单据先后冲抵该单位的未结清单据**，冲完还有剩余才继续留存为预存。可在单据上手动「用预付款抵扣」，也可在收款弹窗里点「仅做抵扣」。
- 同一单位不存在「一边挂欠款、一边躺预存」的两头账：只要有欠款，预存一定已经被用掉了。预存只有在超过该单位全部未结清金额时才会留下余额。
- **客户可用授信 = 授信额度 − max(0, 当前应收 − 预收款余额)**：预收款是客户已经交过的钱，先冲抵欠款，剩下的部分才占用额度；开单校验与客户列表、报表口径一致。
- 建采购/销售单时可填**定金（首付款）**，报表按约定金额判定「定金已付/未付」，不再靠推断。

### 采购应付 / 销售应收明细里「状态」列的口径
状态不再笼统写「已结清 / 部分付款」，而是按**这张单的钱是怎么付的**来显示。每笔分摊都带来源标记（`payment_allocations.source`）：`advance` = 用预存（预付款/预收款）抵扣产生，`cash` = 当次实际收到的现金/转账/定金。单据的「抵扣额 / 现金额 / 欠款额」三个数一比，就得到下面 7 种文案：

| 抵扣 | 现金 | 是否结清 | 状态列显示 |
|:---:|:---:|:---:|---|
| 无 | 无 | — | `未付款` |
| 有 | 无 | 结清 | `抵扣付完` |
| 无 | 有 | 结清 | `现金付完` |
| 有 | 无 | 仍欠 | `抵扣部分+欠款` |
| 无 | 有 | 仍欠 | `现金部分+欠款` |
| 有 | 有 | 结清 | `抵扣+现金付完` |
| 有 | 有 | 仍欠 | `抵扣+现金+欠款` |

- 鼠标悬停在标签上会显示构成明细，例如「已收 ¥300（抵扣 ¥100 + 现金 ¥200）/ 单据 ¥300，尚欠 ¥0」。
- 已退单显示 `已退单`、退单待审显示 `退单待审`——这两种是**单据生命周期**状态（退单的单分摊已释放、待审的单被锁定），优先级高于收付状态，不再套用上面 7 种文案。
- 历史数据在升级时按「付款记录时间早于单据创建时间 = 预存抵扣，其余 = 现金」自动回填来源（`meta.alloc_source_v1`，只执行一次）；此后所有分摊都由业务动作明确写入来源，不再依赖时间推断。

### 销售出库的扣款顺序
提交出库时按固定顺序处理，不会重复收钱：
1. **定金先算已收**：开单时填的定金直接记为已收，从货款里扣掉。
2. **预收款优先抵扣**：余额按金额抵减本单，抵到本单清零为止。
3. **差额才谈收款**：
   - 预收款（含定金）**够付** → 直接抵扣、单据当场结清，**不生成新的收款记录**（钱早就收过了）；
   - **不够** → 弹窗列明「货款 / 定金 / 预收款抵扣 / 本次需另收」，由你选「已收款」（只就差额补一笔收款，单据结清）或「未收款」（差额挂为应收，受授信额度约束）。
4. 出库页合计下方会实时显示这条账（`预收款足够，提交即结清` 或 `本次需另收 ¥X`），随明细、定金、客户变化即时刷新；提交前还会再取一次最新余额，防止页面停留期间退单/收款造成预览与实际不一致。
5. 定金超过货款会被拒绝提交，避免产生「超付分摊」。

### 退单与资金口径
- 单据状态：`active`（正常）→（普通用户申请）`pending_return`（退单待审，锁定，不可收付款/抵扣）→（管理员通过）`returned`（已退单）或（驳回）回到 `active`。
- **`returned`（已退单）不计入应收/应付、往来账余额与客户授信占用**；`pending_return`（退单待审）**仍然计入**——单据只是被锁住，审批被驳回就原样恢复，这笔债权/债务必须还在。财务页的「应收未收 / 应付未付」合计同样包含待审单据（只是额外标出「N 笔退单待审」），因此与客户列表、往来账、应收应付报表始终是同一个数。
- 退单通过时，该单的付款分摊会被删除，已收/已付金额自动**退回该单位的预付款/预收款余额**，钱不会丢；单据与收付款记录本身保留，仅状态变化，便于审计。
- 退回来的钱**不会只是躺在预存里**：若该单位还有别的未结清单据（按单据先后），会立刻被这笔钱冲抵，冲完仍有剩余才留作预存。作废单据、调高收付款金额时同理。
- 退单待审（`pending_return`）期间**保留**原有分摊——一旦审批被驳回，单据恢复原状，已付金额仍在。
- 系统启动时会做两次自愈（各只执行一次，靠 `meta` 标记幂等）：① 清理历史上误挂在**已退单**单据上的分摊；② 把历史上一直没被冲抵的预存余额补冲到该单位的未结清单据（总额不变，只是把钱指回具体单据）。两次的释放/冲抵金额都会打印在启动日志里。
- 「约定了定金却还没生成定金收付款」的历史单据，其定金记录只在**首次升级到本版本时补建一次**（同样靠 `meta` 标记）。因此如果某笔定金记录被人工删掉（例如当初录错），重启服务**不会**再把它补回来——金额要恢复请重新录入或调整单据定金。

采购、销售、盘点、收付款均在数据库事务中完成，数字保证一致。

**录入校验**（后端强制，前端拦不住也能兜住）：

- 数量必须是大于 0 的整数且不超过 10 亿（避免 `2.5` 被悄悄截成 `2`，也避免一次把库存灌到天文数字）；
- 单价必须明确填写且是不小于 0 的有限数字（空值、负数、NaN、`Infinity` 一律拒绝）。特别注意 **`1e999` 这类值会被 JSON 解析成 `Infinity`，而 `Infinity > 0` 为真**，曾经能绕过所有「大于 0」的校验：写进库后接口返回 `null`（页面显示 ¥0）、所在单位的单据会被无限抵扣、Excel 导出会损坏文件；
- 采购单价填 0 时**不会**覆盖商品进价（否则该商品此后的每张销售单成本都变 0、毛利虚增 100%），但货照入库存；
- 定金不得为负、不得超过本单货款（否则会生成「超付分摊」，应付/应收变负数）；
- 收付款的往来单位类型由方向决定（付款只能是供应商、收款只能是客户），传错直接拒绝；
- **钱的流向必须与单据类型一致**：付给供应商的钱只能分摊到采购单，收客户的钱只能分摊到销售单，交叉一律拒绝；
- 已退单 / 退单待审的单据不接受收付款与预存抵扣；退单待审期间，分摊到该单的那笔收付款**既不能调金额也不能删除**（否则退单流程无法还原，钱会彻底消失）；
- 商品建档：进货价/销售价/初始库存/预警值均不得为负，库存调整量与调整后余量都有上限；
- 单张单据最多 500 行明细，单次付款最多关联 200 张单据，请求体上限 1 MB。

**操作权限**（越权行为一律 403）：

- 删除商品、改动客户授信额度、修改收付款的归属单位、删除收付款记录、作废单据、退单审批 —— **仅管理员**。其中客户授信额度是唯一的赊账风控闸门，普通用户若能自行调高就相当于把风控开关交给了被风控对象，因此编辑客户资料时该输入框对普通用户是禁用的。
- 其余日常操作（开单、收付款、新建/编辑商品与往来单位）普通用户照常。

**会话与登录**：

- 每次请求都会回库确认账号仍然存在——管理员删除某账号后，该账号已发出的会话**立即失效**（原来最长还能用 7 天）。
- 登录连续输错 5 次会锁定 10 分钟（按「IP + 账号」限流，成功即清零）；密码长度上限 200 位，避免超长串反复触发 bcrypt 造成 CPU 放大。

**收付款可分摊的单据范围**：不分月份，任意「未结清且生效中」的采购/销售单都能选（收付款弹窗打开时会按全量拉取一次，不受页面时间筛选影响）。

### 删除收付款的留痕（`payment_deletions`）

删一笔收付款，等于把已经发生的资金往来从账上抹掉，而且它比作废单据更难追：单据作废好歹还有 `doc_voids` 记着谁删的，而这类删除原本什么都不留——更隐蔽的是 `payment_adjustments` 的外键是 `ON DELETE CASCADE`，删一笔钱会把它全部的**调账审批历史**（谁申请改成多少、谁批的、什么时候批的）一起删光。

所以删除前会先把三样东西整体快照存档：记录本体 + 分摊去向（含单号） + 即将被级联删除的审批历史。台账存在 `payment_deletions` 表，管理员可查 `GET /api/payment-deletions`。

### 资金口径的两个「容易看漏」的地方

这两项都属于**防御性缺口**：当前库里没有脏数据，但一旦出问题，账面上的数字不会自己报警，只能靠人肉发现。现在都做了显性化处理。

**① 预存余额为负。** 某单位「分摊出去的钱」多于「实际收付的钱」时，余额就是负的。可用额度必须按 0 处理（拿负数去抵扣等于凭空造钱），所以它被抹平后平时完全看不见——但账面缺口是真实存在的，典型成因是金额调整审批通过后把金额改小了、而分摊没跟着缩回去。

- `advanceRawOf()` 返回**真实余额**（可为负），`advanceBalanceOf()` 返回**可用额度**（负数按 0）；
- 数据体检新增 `negative_advance` 检测项（error 级），列出每个负余额单位与缺口金额。

**② 无归属收付款。** `party_id` 为空的钱不属于任何客户/供应商，既进不了任何一家的预存余额，也不会参与自动抵扣——这正是「实际收到的钱」和「各单位预存合计」对不上时的差额所在。

- `/api/finance/summary` 返回 `orphans: { count, balance }`；财务页在有余额时会在卡片下方直接提示金额与处理入口；
- 数据体检新增 `orphan_payment` 检测项（warn 级）。

> 注：若一笔无归属款项已经全额分摊到单据上，它的未分摊余额为 0，就不算「躺在账外」，体检测不会告警。

### 报表导出的口径

`/api/reports/export` 生成的 Excel 里，「全量」和「本期」两套口径是**混排**的，所以概览表每一行都标注了口径，避免把余额快照当成本期发生额去相加：

- **全量（截至导出时刻的余额）**：总应收/总应付/净头寸、按客户应收明细、按供应商应付明细、库存商品金额；
- **本期（`from` ~ `to`）**：本期销售/采购金额与利润、本期退单、本期改价记录、收付款流水。

退单的归月口径也已统一：**已审批完成的按 `returned_at`，仅到「待审」的才退回 `return_requested_at`**，与退单报表页面一致。原来导出里两个字段的顺序写反了，跨月审批的退单会在报表页和导出表里落进不同月份，同一份账导出两次数字对不上。

导出还加了保护：改价记录的期间筛选下推到 SQL（原来是先取最近 5000 条再内存过滤，超出部分会被静默截掉），收付款流水单次上限 50000 笔，超限时会在概览页写明并提醒缩短期。

客户/供应商的「交易清单」导出另设单次 **20000 笔**上限（`EXPORT_MAX_ROWS`）：`buildWorkbook` 是**同步**生成 ZIP，几万行会把主线程占满数秒，期间所有接口（连登录都算）全部无响应。超限时只截断**明细**（取最近 20000 笔），**合计行仍按全量计算**，并在表头标注「⚠ 单次最多导出 N 笔…下方合计仍为全量」，避免被当成完整数据对外提供。

### 打印与导出的口径

- **看到的 = 导出的**：所有导出接口都接收与页面完全相同的筛选参数，且页面与导出在服务端**共用同一个计算函数**（`financeSummaryData` / `partyLedgerData` / `partyLedgerPayData`）。各写一套筛选解析，早晚会出现「屏幕 72 笔、导出 70 笔」这种极难察觉的差异。
- **打印一律走独立窗口**，不用 `window.print()`：页面里的明细表套在 `.table-scroll`（`max-height: 460px`）里，直接打印只能印出屏幕上可见的十来行。独立窗口可以指定 A4 横向/纵向、跨页自动重复表头，还能让用户「另存为 PDF」。
- **单据打印带金额大写**：按四位分节（个 / 万 / 亿）计算，`100.05` → 壹佰元零伍分，`1,002,000` → 壹佰万零贰仟元整。没有采用网上流传的「逐位 + 单位表」写法——那类实现在这两个数上会漏掉中间的「零」，印在单据上就是错票。
- **单家往来流水账的日期段只筛明细**：未结清余额（`outstanding`）与预存余额始终按全量算。若把三者都按区间裁开，「单据合计 − 已付 = 未结清」这个等式在筛过日期的页面上必然不成立，表尾会显得自相矛盾。因此筛选态下表尾同时写明「本期间单据 / 已付」与「当前未结清（全量）」。

### 金额取整口径（`lib/num.js`）

所有金额一律走 `r2` 四舍五入到分，**唯一实现放在 `lib/num.js`**，`db.js`（含启动时的自愈迁移）与 `server.js` 都从这里取。前端 `public/js/app.js` 因为浏览器无法 require，保留一份等价副本，改算法时两处必须同步。

为什么要这么较真：`Math.round(x * 100) / 100` 与 `r2(x)` 在边界值上会差 1 分钱。1.005 在计算机里的真实值是 1.00499999999999989…，直接乘 100 得 100.4999… 舍到 ¥1.00；`r2` 带浮点纠偏后舍到 ¥1.01。在 0~100 范围内采样有十几个值会分叉（0.145 / 0.285 / 1.005 / 1.015 …），而 `(总额 − 已付)`、`(本次收取 − 剩余额度)` 这类中间量天然就会产生这种非整分值。

实现上必须避开两个坑（详见 `lib/num.js` 顶部注释）：

1. **纠偏量的大小必须跟数值本身成正比**。早期写法是 `Math.round((v + Number.EPSILON) * 100) / 100`（加一个绝对常量），它对 1.005 有效，但 v 一旦超过 2，`Number.EPSILON`（≈2.22e-16）已小于 v 的 1 个 ULP，加上去等于没加，补偿静默失效——属于「碰巧正确」。现改为 `v * (1 + Number.EPSILON * 4)`：double 乘 100 引入的相对误差约 1e-16，抬 4 倍足以跨越 .5 判定边界，又远小于半分，不会把本该舍去的 0.0049 抬成 0.01。
2. **`Math.round` 对负数不是四舍五入，而是向 +∞ 靠拢**。`Math.round(-100.5)` 得 `-100` 而不是 `-101`，于是 `-1.005` 会得到 `-1.00`，与正数方向不对称。现改为取绝对值计算后补回符号。60 万个三位小数样本（含正负）对照「十进制真值半进位」实测：不带符号处理的旧实现错 **3 万**个，现实现 **0** 个。

`r2` 遇到 NaN / Infinity 会**原样返回**而不是抹成 0：一旦在这里洗白，脏数据就查不出是哪个环节算出来的。

危害在于**两边口径不一致**：启动时的自愈迁移用截断口径写库、运行时用进位口径读出来展示，同一笔账就成了「库里 ¥1.00、页面 ¥1.01」。差额小到日常发现不了，往往要逐笔对账到分时才暴露。已修的自愈迁移 `fixOverAllocated()` 正属此类——它截断超额分摊时写入的数，必须与运行时统计的读法完全一致，否则单据会凭空欠 1 分钱，而这笔钱其实已经退回预存了。

同理，这也是为什么收付款 Excel 导出、**改价记录**里的金额都统一走 `r2`：导出的数据要能直接和账面核对，不能各自舍入成不同的数。

### 成本核算：批次 FIFO 模型（同品不同供应商 / 批次价差）

同一个商品从不同供应商采购、或同一供应商不同批次进价不同，是常态。本系统用**批次（FIFO 先进先出）**模型精确核算成本，核心思路：

- 每笔采购入库的**每一行** = 一个独立**批次**（`inventory_lots` 表），记录 `供应商 / 批号 / 单价 / 数量 / 剩余量`。同品不同供应商、不同批次的不同进价，在库存里就是多条批次记录，天然分开。
- **销售出库成本**按 FIFO 从最老批次实际消耗计算，精确落到 `sale_items.cost`（单位成本）与 `profit`（= 收入 − 精确出货成本），不再用「商品单一标准进价」一刀切。
- **报表货值**沿用原 `stock × purchase_price` 口径，但 `products.purchase_price` 现在维护为「剩余批次的加权平均单价」。数学上 `stock × 加权均价 ≡ Σ(批次剩余量 × 批次单价)` = FIFO 在库货值，所以**原有报表无需改写即精确**。
- **退单 / 作废 / 盘点调整**都会同步维护批次：采购退单 FIFO 扣减批次；销售退单 / 作废按本单实际成本建「退回批次」；盘盈建调整批次、盘亏 FIFO 扣减。每次操作后重算加权均价，保证 `stock × purchase_price` 始终等于批次货值。

为什么要这么做：旧模型把 `products.purchase_price` 直接覆盖成「最近一次采购价」，一旦价格波动，库存货值与销售成本都会系统性失真（例：¥10 进 100、卖 50 后 ¥12 进 100，旧模型会把货值算成 150×12=1800，真实应为 50×10+100×12=1700）。批次 FIFO 从根上消除这类偏差。

**迁移（首次部署生效，幂等）**：服务启动时 `rebuildLots()` 自动从历史 `purchase_items` 重建批次（每个采购明细 = 一个历史批次），再用 FIFO 把批次总量对齐到当前库存；有库存但无采购单历史的商品（手工建档 / 期初导入）按其当前进价建「期初」批次；历史盘盈差额补「调整」批次。已建过批次的库不会重复执行（由 `meta` 标记保护）。

**查看批次**：库存管理页每行「批次」按钮 → 弹窗按 FIFO 顺序展示各批次的供应商、批号、单价、剩余/总量、入库时间，以及加权均价与在库货值。

> 注：历史已结账的销售单 `sale_items.cost` 保持迁移前原值不回溯；FIFO 成本自部署上线后开始精确。新建带「初始库存」的商品会自动建账批次，可正常 FIFO 出库。

### 商品批量导入（模板导出 / 导入 / 未导入表）

商品管理页右上角两个按钮：

- **⬇️ 下载模板**：生成 `.xlsx`，含「商品导入模板」（仅表头一行，避免示例行被误导入）与「填写说明」两个工作表。列：`商品编码 / 商品名称 / 分类 / 单位 / 进货价 / 销售价 / 初始库存 / 库存预警值 / 备注`。
- **⬆️ 导入商品**：选择 `.xlsx` 或 `.csv`（UTF-8）。前端把文件读成 base64 走 JSON 上传，**无需额外上传中间件**。服务端逐行解析并按下列规则处理：

| 情况 | 处理 |
| --- | --- |
| 商品编码在**库中已存在** | 跳过，进「未导入表」（原因：商品编码已存在，含库内同名商品） |
| 商品编码在**本文件内重复** | 先到的导入，后到的进「未导入表」 |
| 商品名称**为空** | 跳过，进「未导入表」 |
| 进货价/销售价/库存/预警值**非法**（负数或非整数） | 跳过，进「未导入表」（须为 ≥0 的数字；库存/预警值须为 ≥0 整数） |
| 其余（含**无编码**的行） | 导入。若初始库存 > 0，自动写「初始库存（批量导入）」流水并建立「期初」批次（与手工建档口径一致） |

导入结果弹窗会显示「导入成功 / 共 / 未导入」数量与逐行原因；存在未导入行时提供 **⬇️ 下载未导入表**（保留原行 + 「未导入原因」列）。

> 说明：编码去重按**精确文本**比较（区分大小写）。若需忽略大小写或前后空格，导入前请先统一编码格式。升级到本功能后无需迁移数据库结构。

### 侧栏背景音乐

在「系统配置 → 侧栏背景音乐」勾选「显示背景音乐播放器」并保存后，左侧菜单栏「系统配置」下方会出现一个紧凑播放器（播放/暂停、上一首/下一首、音量，切歌列表按文件名循环）。

- **音乐目录固定**为项目根目录下的 `mp3/`，不可更改；服务启动时自动创建该目录（并附带一份说明文本）。把 `.mp3` 文件直接拷贝进 `mp3/` 目录即可，无需在系统内上传。
- 播放器列出该目录下所有 `.mp3`（大小写不敏感），支持中文文件名；放入新文件后点播放器上的 `⟳` 刷新列表。
- 音频通过 `GET /mp3/:file` 播放，走登录鉴权并支持 HTTP Range（可拖动进度）。仅允许 `mp3/` 目录内的 `.mp3`，拒绝路径穿越。
- 开关为全局配置：管理员保存后对所有账号生效；其它已登录端会在每 60 秒的侧栏刷新时自动同步显隐。
- 浏览器禁止无交互自动播放，首次通常需点一下 ▶；从「关闭」切到「开启」并保存时，因保存本身是用户操作，会尝试自动开始播放。
- 手机端（≤768px）侧栏变为底部标签栏，播放器自动隐藏。

### 插播广播

在「系统配置 → 插播广播」勾选「启用插播广播」并设置**播放间隔**（秒）后，每隔一个周期就插播一条广播。**该功能独立于背景音乐**：音乐在播就先暂停、播完自动续播；音乐没在播（甚至音乐开关关闭）也照常按周期插播。

- **广播文件放在项目根目录下的 `Broadcast/` 文件夹，条数不限**。文件名格式固定为 `guangbo-词序号-本轮位置.mp3`，两个数字都可用 1~9（更大也行，按数值排）：
  - 第一个数字：这是第几条广播**词**（仅用于标识是哪一句）；
  - 第二个数字：这一句在「一轮插播」里排**第几个**，播放顺序只看它。
  - 例如一共有 3 句广播词、一轮排 4 条、第 3 句要播两次，就放 `guangbo-1-1.mp3`、`guangbo-2-2.mp3`、`guangbo-3-3.mp3`、`guangbo-3-4.mp3`：**每次只播一条，下一次到点播下一条，按顺序轮播，一轮播完从头再来**。
  - 兼容旧版单文件 `guangbo.mp3`（当作 1-1）；只有当目录里没有任何 `guangbo-N-N.mp3` 时它才顶上，避免和 `guangbo-1-1.mp3` 撞成同一条被播两遍。
  - 服务启动时自动创建该目录（并附带说明文本）。把文件拷进去即可，替换后无需重启（后台每 60 秒自动重新探测，最长约 1 分钟生效）。
  - 接口不接收任意路径：音频请求只认服务端扫描白名单里的文件名，从根上排除路径穿越。
- **播放间隔**默认 `120` 秒，允许 `30 ~ 3600` 秒；非法或越界值会被夹到区间内（后端 `getSettings` 与 `PUT /api/settings` 同一口径），局部更新时未传的字段保持不变。
- **计时口径**：按实际经过时间连续累计，**与音乐是否播放无关**。广播自身占用的时长不计入下一个周期（播完从 0 重新计时）。侧栏倒计时按**整数秒**显示（向上取整，不会出现「还有 0 秒」）；播放中显示「📢 插播中 N/总数」，空闲时显示「📢 下一句 N/总数 · X 秒」。
- **与音乐的关系**：音乐正在播时，插播会先暂停音乐、广播播完自动续播；音乐没在播时，插播结束后保持原来的静音状态，不会替你打开音乐。
- **只开广播不开音乐**：左侧菜单仍会显示一条带倒计时的广播信息（隐藏音乐控件），可看到「📢 下一句 1/4 · 87 秒」这类提示。
- **文件缺失**：`guangbo.mp3` 不存在时，本次插播静默跳过、音乐不中断，状态行提示「未找到 Broadcast/guangbo.mp3」；下个周期自动重试，补上文件后无需重启。
- **手动干预**：音乐在播时，广播播放中点 ▶ 视为「跳过本次广播」，立即恢复音乐；点 ⏭/⏮ 会中止广播并切歌。音量滑条对音乐与广播同时生效。
- **浏览器自动播放限制**：若用户从未与页面交互（例如只开广播、一直不操作），浏览器可能拒绝播放音频，此时状态行提示「浏览器阻止了自动播放，点一下页面任意处即可继续插播」，用户点一下后恢复正常。
- 音频通过 `GET /api/broadcast/audio` 播放（登录鉴权、支持 Range）。该接口**不接收任何文件名参数**，路径在服务端写死，从根上排除路径穿越；`GET /api/broadcast/info` 返回开关、间隔与文件是否存在（URL 带「大小+修改时间」版本号，替换文件后不会命中旧缓存）。
- 部署时 `Broadcast/` 目录随项目一起部署即可，**不需要**把它排除在备份之外（目录很小，且只是音频文件，不影响数据库备份）。

### 部署约束：必须单进程运行

本系统**不能**用 PM2 cluster、Node.js `cluster` 或任何多实例方式部署，两个隐式前提决定：

1. **SQLite 只有一个写者**。`better-sqlite3` 直连本地文件，WAL 只让「读写」并发，**写与写仍互斥**。多进程会让 `SQLITE_BUSY` 急剧增加——即便 `db.js` 已设 `busy_timeout = 10000` 让请求排队，吞吐量也远不如单进程串行写。
2. **会话存在内存里**。`express-session` 默认用的是内存存储，进程间不共享。多实例时用户会被随机打到不同进程，表现为「刚登录就被踢出、反复掉线」。

这两件事都不会直接报错，只会表现为偶发 500 和偶发掉线，很难归因。所以：

- 启动日志会**主动检测** `NODE_APP_INSTANCE`（PM2 多实例标志）并打印醒目告警；
- 若确需交给 PM2 管理，请务必单实例：`pm2 start server.js -i 1`。

### 版本管理：哪些东西绝对不能提交

根目录的 `.gitignore` 已排除四类内容，**前两类一旦提交就无法撤回**（会永久留在 git 历史里，即使后来删除）：

- `data/`（含 `*.db`、`*.db-wal`、`*.db-shm`、`backups/`）：全部客户资料与账目明细；
- `.session_secret`：登录态签名密钥。拿到这个文件就能**伪造任意用户（含管理员）的会话**，等价于交出全部权限；
- `node_modules/`：依赖目录，`npm install` 可重建；
- `mp3/`、`Broadcast/`：音频素材（本项目 `mp3/` 约 79MB）。若希望音乐/广播随代码一起版本管理，删掉这两行即可。

> 当前目录**尚不是** git 仓库，这份 `.gitignore` 是为将来做版本管理或上传备份预留的。真要入库前，先看一眼 `git status`，确认 `data/` 与 `.session_secret` 没被带进去。

### 会话说明：重启会要求重新登录

会话数据在进程内存里，**服务重启后所有已登录用户都会被登出**，需要重新登录（数据本身不受影响）。这是有意取舍：本地/单机部署省去一套 Redis 或持久化会话，少一个依赖、少一份要备份的东西。

另外，管理员在系统里删除某个账号后，该账号已发出的会话会**在下一个请求即失效**（每次请求都会回库确认账号是否还存在），不会继续用到 cookie 过期为止。

### 并发写保护与重复提交拦截

**写锁**：`db.js` 初始化时设置了 `busy_timeout = 10000`：同一时刻 SQLite 只允许一个写事务，后来的写请求会排队等待而不是立刻失败。（`better-sqlite3` 默认已是 5000ms，这里显式写一遍是防止后续改动 `new Database(..., { timeout })` 时被无意取消，同时放宽到 10s 以覆盖启动自愈迁移这类长事务。）

**重复提交**：前端在 `document` 捕获阶段挂了一个统一的 submit 守卫——表单提交时立刻禁用按钮并显示「处理中…」，由「`api()` 未完成请求数归零」判定何时恢复（handler 常常在 `await api()` 之后还要再拉一次列表刷新，所以按请求计数比固定延时更准），并带 30 秒硬超时兜底，断网 hang 住也不会把按钮永久锁死。这样收口到一处，7 个表单（登录、商品、往来单位、采购、销售、收付款、库存调整）自动生效，不需要在每个 handler 里记得写。

注意这只是**体验层**拦截：真正的资金安全仍然由后端保证——单号唯一约束、库存不足校验、金额上限校验都在服务端。

## 数据备份与还原

- **手动备份**：系统配置页 →「数据安全 · 备份」→「立即备份并下载」，得到一个 `.db` 文件，可存到 U 盘/网盘。
- **自动备份**：服务每天首次启动时自动把数据库复制到 `data/backups/auto-YYYYMMDD-HHMMSS.db`，只保留最近 7 份。想多留几天，把文件复制出去即可。
- **还原**：先关闭服务 → 用备份文件覆盖 `data/inventory.db` → **删除** `data/inventory.db-wal` 与 `data/inventory.db-shm` → 重新启动。
